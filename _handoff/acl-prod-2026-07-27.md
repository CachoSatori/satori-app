### Cómo leer `proacl` (la trampa del PUBLIC)

- Un item que empieza con `=` **sin rol antes** ES **PUBLIC**. `=X/postgres` → PUBLIC tiene EXECUTE y
  **`anon` lo hereda**, tenga o no un grant `anon=X` propio.
- Supabase, por default, además otorga EXECUTE explícito a `anon, authenticated, service_role` en cada
  función nueva → de ahí los items `anon=X` explícitos en 4 de las 5.
- **`delete_movement_cascade` NO tiene item `anon=X`** (la mig 044 le hizo `revoke ... from anon`) y
  **aun así `anon=true`**: hereda por el `=X` de PUBLIC que nunca se revocó. Es exactamente la trampa
  que documenta el encabezado de `acl-funciones.ts` → un `revoke ... from anon` a secas NO alcanza.
- Las 5 seguras (`✅`) no tienen `=X` ni `anon=X`: se crearon/blindaron con `revoke all ... from
  public, anon` (patrón mig 045), dejando solo `authenticated` + `service_role`.

### `revoke` propuestos (patrón mig 045 — quita PUBLIC **y** anon, deja authenticated + service_role)

```sql
-- 1) ALTA — plata directa
revoke all on function public.delete_movement_cascade(uuid, text, text, text) from public, anon;

-- 2) MEDIA — auditoría de facturas
revoke all on function public.mark_factura_verified(uuid) from public, anon;

-- 3) MEDIA-BAJA — trigger de contabilidad (seguro: no frena el trigger)
revoke all on function public.unif_on_cash_movement() from public, anon;

-- 4) BAJA — trigger de alta de usuario (seguro: no frena el signup)
revoke all on function public.handle_new_user() from public, anon;

-- 5) BAJA / ⚠️ EVALUAR EXCLUIR — ver nota antes de tocar
revoke all on function public.get_my_role() from public, anon;
```
